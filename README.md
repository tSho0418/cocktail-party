# cocktail-party

カクテルのレシピと写真を共有する日本語の Web SNS。用語は [CONTEXT.md](CONTEXT.md)、要件は [docs/requirements.md](docs/requirements.md)、設計判断は [docs/adr/](docs/adr/) を参照。

## Stack

SvelteKit (SSR, adapter-vercel) + Tailwind CSS, Hono API mounted at `/api/*` via `src/hooks.server.ts`, Drizzle ORM on Neon Postgres.

| Path                          | Role                                                       |
| ----------------------------- | ---------------------------------------------------------- |
| `src/lib/server/api/app.ts`   | Hono app (`/api/*`). Thin routes only.                     |
| `src/lib/api.ts`              | Typed Hono client (`createApiClient(fetch)`).              |
| `src/lib/server/services/`    | Business logic, shared by load functions and Hono routes.  |
| `src/lib/domain/alcohol/`     | Alcohol Content rules (pure); also run in the browser.     |
| `src/lib/server/db/schema.ts` | Full data model. Migrations in `drizzle/`.                 |
| `src/lib/server/auth/`        | Better Auth (Google/LINE) and Hono guards. See Auth below. |

## Run

Requires Node 22, pnpm 9 (`corepack enable`) and Docker (for the local Postgres).

```sh
pnpm install
cp .env.example .env        # defaults point at the docker-compose Postgres
pnpm db:up                  # postgres:17 on 127.0.0.1:5432, or reuse one already running there
pnpm db:migrate             # apply drizzle/ (incl. pg_trgm)
pnpm db:seed:ingredients    # initial Ingredient master (DT-001), idempotent
pnpm dev                    # http://localhost:5173
```

`db:*` scripts read `DATABASE_URL` from the shell, not `.env` (drizzle-kit does not load it), and default to `postgres://postgres:postgres@localhost:5432/cocktail_party`.

### DB tests and parallel worktrees

`DATABASE_URL_TEST` names only the server and credentials (default `postgres://postgres:postgres@localhost:5432/postgres`). Each `pnpm test:db` run creates its own database `cocktail_party_test_<random>`, applies `drizzle/`, runs the tests and drops it afterwards, also when tests fail. Several worktrees can therefore share one Postgres and run `pnpm test:db` at the same time. A run killed hard (e.g. `kill -9`) can leave a `cocktail_party_test_*` database behind; drop it by hand.

The query-plan check on ~2,000 generated Recipes is skipped unless `EXPLAIN_SEARCH` names a report file: `EXPLAIN_SEARCH=/tmp/explain.txt pnpm test:db search.explain`.

The app database is shared, though: worktrees using the same `DATABASE_URL` see each other's data, and `pnpm db:reset` resets it for all of them. Give a worktree its own `DATABASE_URL` database name if that matters.

### Notes

The first migration enables `pg_trgm` by a line added by hand to `drizzle/0000_init.sql`; drizzle-kit does not emit `CREATE EXTENSION`.

The DB client (`#lib/server/db`) uses node-postgres. Locally it talks to the compose Postgres. The Preview currently uses Neon's **Direct** string; switching to Pooled is undecided, see "Preview" below. For node-postgres write `sslmode=verify-full` in the string (not for `pg_dump`, see "Preview").

The pool is small on purpose (`max: 5`, idle connections closed after 5 s, 10 s to connect); the reasons are in the comment in `src/lib/server/db/index.ts`. Every connection has a permanent `error` listener (pg-pool only listens while a connection is idle, so one held by a transaction would otherwise crash the process when the server cuts it), and the pool is passed to `attachDatabasePool` from `@vercel/functions`, which keeps a Fluid compute instance alive until idle connections are closed so a suspended instance does not leak them (Vercel's guide "Connection Pooling with Vercel Functions"). It is still marked `@experimental` in the package and does nothing outside Vercel, so it has not been seen working here; the db tests cover only the pool settings and the `error` handling.

## API

Routes live in `src/lib/server/api/` and only validate the request shape, call a service and map its result to a status; `AppType` (from `createApp()` in `app.ts`) types `createApiClient` in `src/lib/api.ts`. Errors are `{ "error": "<code>" }`: 400 malformed request, 401 signed out or Suspended, 403 no Username / not the owner / not an Administrator, 404, 413 body too large, 409 duplicate Ingredient (with `similar`), 422 a rule of the service rejected the input (the code is the service's, e.g. `main_photo_required`).

Photo ownership (ADR 0006): `POST /api/photos` records the uploader in `photo_upload` (one row per upload, keyed by the `<uuid>` in the key). `POST`/`PUT /api/recipes` accept only `recipe/<uuid>/{list,detail}.webp` keys whose upload row belongs to the signed-in Member; another Member's upload, a Member icon, an unknown or malformed key is 422 `photo_key_invalid`. Only the uploader can reference an upload, so nothing else can still use a photo once its upload is released. When an edit or delete leaves an upload referenced by no Recipe, the same transaction deletes its `photo_upload` row (so it can never be attached again) and the caller (the Recipe routes, the `/admin` Recipe deletion, the sweep) then deletes both objects with `deleteObjects` (`services/images/delete-objects.ts`), best effort after commit: a storage failure, including missing `R2_*` variables, does not fail the request; each key it could not delete gets one `photo cleanup failed` log line. The write takes the locks listed under Lock order, so a concurrent Recipe write cannot reference a photo that is being deleted. Uploads that are never attached (abandoned form, replaced photo, failed publish) are removed by the sweep (`pnpm photos:sweep`, `sweepUnusedUploads` in `services/images/sweep.ts`): uploads older than 24 hours that no Recipe photo and no Member icon references have their row deleted (rows locked `FOR UPDATE SKIP LOCKED`, references re-checked), then both objects. It needs `DATABASE_URL` and the `R2_*` variables; `.github/workflows/sweep-photos.yml` runs it (manual only, and only from `main` so other branches never reach the `production` secrets, until those secrets exist; see Known limits). Recipes written before this change have no upload rows; they keep working, and an edit may resend the keys the Recipe already uses, as long as they have the shape `recipe/<uuid>/{list,detail}.webp` (an older key shape is rejected with `photo_key_invalid`).

Member icons follow the same rule: `updateProfile` accepts only a `member/<uuid>/list.webp` key whose `photo_upload` row (`kind = 'member'`) belongs to the Member (`icon_key_invalid` otherwise; the current icon is always accepted), and an icon that is replaced or removed has its row deleted in the same transaction and its objects deleted after commit.

**Lock order** (ADR 0006, #40, #45): a transaction that locks Recipes, photo uploads, Ingredients and a Member takes them in this one order, each kind in id order, skipping the kinds it does not need: **Recipe rows, then `photo_upload` rows, then `ingredient` rows, then the `member` row**. `updateRecipe` and `deleteRecipe` lock the Recipe (`lockRecipe`), then the uploads of its old and new photos (`lockPhotos`); `updateRecipe` then share-locks the Ingredients it uses (`loadIngredients`, `FOR SHARE`: an ABV edit waits for it, and shares do not wait for each other); `createRecipe` has no Recipe row yet, so it locks the uploads, then the Ingredients, and its INSERT then takes the Member's `FOR KEY SHARE`; `updateIngredientAbv` (FR-015) locks the Recipes that use the Ingredient, then the Ingredient row, and then reads those Recipes again: one that started using the Ingredient in between is not locked, and locking it now would be out of order, so the transaction ends without writing and a new one starts, once for each such edit that commits in that gap; `updateProfile` locks the icon uploads, then the Member row; `withdrawMember` locks all of the Member's Recipes, then all of their uploads, then the 0% Ingredients they registered (#64), then the Member row, before the cascading DELETE; the sweep locks upload rows only, with `SKIP LOCKED`; `deleteIngredient` (#64) locks only the Ingredient row, `FOR UPDATE`, which waits for a Recipe write's `FOR SHARE` on it and then finds the Ingredient in use. Following the order is what lets a withdrawal and a Recipe write by the same Member, or a Recipe edit and an ABV edit, both finish instead of deadlocking. The one place that does not follow it exactly is the withdrawal's cascade, which sets `ingredient.created_by` to null last, after the `member` row is deleted (in effect Member, then Ingredient); no combination that deadlocks through it has been found.

Ingredient limits and cleanup (#64): FR-012 lets any Member add a 0% Ingredient without approval, so `createZeroAbvIngredient` counts the Member's rows by `ingredient.created_by` and answers 429 `ingredient_daily_limit` beyond 5 in the last 24 hours and 429 `ingredient_total_limit` beyond 30 in all (`src/lib/domain/ingredient-limits.ts`; provisional values; the picker shows both as messages). The check runs after the duplicate check, so a Member at the limit still learns which existing Ingredient to pick, and under a per-Member `pg_advisory_xact_lock` (`lockIngredientQuota`) taken before the name lock (the Member lock, then the name lock), so simultaneous requests cannot pass the limit. **An Administrator is not limited**, unlike the daily limits of #63, which count Administrators too: an Administrator can already add any number of alcoholic Ingredients (they are not counted), so limiting their 0% ones would protect nothing, and it would only get in the way of maintaining and seeding the master. `ingredient.created_by` is nulled when the creating Member withdraws, which would hand the next account a fresh quota and leave the rows behind; so `withdrawMember` deletes the 0% Ingredients the Member registered that no Recipe uses once their own Recipes are gone (it takes the quota lock first, then locks those rows between the uploads and the Member row, as the Lock order says), and keeps the ones another Member's Recipe uses (with `created_by` null). Rows an Administrator deletes stop counting too; that is accepted (the Administrator chose to). Size of the master: the seeded ~80, plus at most 30 per current Member, plus the ones a withdrawn Member registered that someone else's Recipe still uses (so a withdraw-and-return loop leaves nothing unused behind); this is what the top page's `listIngredientOptions` reads whole. `/admin` shows every alcoholic Ingredient (the Administrator's own, so bounded) but only 50 of the 0% ones at a time, narrowed by `?q=` (name search, normalized like duplicate detection; "N 件中 50 件を表示"), with "in use" worked out by one correlated `exists`, not a query per row; it stayed fast with 5,000 throwaway 0% rows. `GET /api/ingredients/suggest` returns at most 20 items and scans the master without an index: `similarity()` and the two `strpos()` containments cannot use a pg_trgm GIN index (only `%`/`LIKE '%x%'` can, and `LIKE` is not used for names under 3 characters), so none was added; on 5,000 throwaway rows (random katakana names) `EXPLAIN ANALYZE` measured about 40 ms (a Seq Scan). `ingredient.created_by` has no index: the limit check and the withdrawal read it with a Seq Scan over a table of this size (the existing foreign key's `SET NULL` on withdrawal does the same). An Administrator deletes an Ingredient on `/admin` behind a `<details>` confirmation (`deleteIngredient`, 0% only; `in_use` while a Recipe uses it, and `not_deletable` for an alcoholic one: the curated spirits list, and OOS-007 and #58 are left alone). A Recipe form that still holds a deleted Ingredient gets `unknown_ingredient`. `pnpm db:seed:ingredients` matches by name, so running it again brings back a seeded Ingredient an Administrator deleted.

Publishing is idempotent when the client sends an `idempotencyKey` (ADR 0007, #46): `RecipeForm` makes a UUID per publish attempt, reuses it while the form body is unchanged (a resend after a lost response) and makes a new one when the Member edits the form. `recipe.idempotency_key` is nullable with a partial unique index on `(member_id, idempotency_key)` (keys are per Member). `createRecipe` first looks the key up (a plain SELECT, no lock, so the Lock order is unchanged) and, if found, returns that Recipe before the photo check (the first request already used the photos, and an edit may have released them); a request that loses the race hits `ON CONFLICT (member_id, idempotency_key) WHERE idempotency_key IS NOT NULL DO NOTHING` (any other unique violation still throws) and returns the winner's Recipe. Its INSERT may wait for the winner's transaction, which has taken all its locks already, so the wait cannot form a cycle; with the same photo the loser waits earlier, in `lockPhotos`. Requests without a key behave as before.

Daily limits (#63, `services/quota`): the free tiers have no room for one account to fill them, so each Member gets `DAILY_LIMITS` = **40 photo uploads and 10 new Recipes per rolling 24 hours**. Over the limit, `POST /api/photos` answers 429 `photo_daily_limit` and `POST /api/recipes` 429 `recipe_daily_limit`; the form shows why. The numbers sit above honest use (a Recipe takes at most 4 photos, so 10 Recipes need 40; **every upload attempt counts, also a refused or undecodable one and a photo picked again**, so a Member who publishes fewer than 10 Recipes a day has room for retries) and far below abuse. Editing a Recipe is not counted, and neither is a resent idempotency key (it returns the Recipe the first request made, before the limit is looked at). Administrators are counted like Members: the operator needs no more, and a stolen administrator session is the one that must not be unlimited.

How it is counted: each use is a row in its own table, `quota_use` (`(member_id, kind, created_at)` indexed, rows go with the Member), not a count of `photo_upload` or `recipe`: those rows disappear when a Member deletes the Recipe, so upload, publish, delete in a loop would never reach the limit. A request **takes its use first** (`reserveQuota`): a cheap SELECT refuses a Member who is plainly over the limit without writing; otherwise it INSERTs its row (a statement of its own, committed at once, so every other request sees it) and then counts the last 24 hours including itself, and deletes its own row and answers 429 if that is over the limit. Because the row is visible before the slow work (sharp, R2) starts, the number of uploads in flight cannot be used to get past the limit: of any set of accepted requests the one that inserted last has counted all of them, so **never more than the limit is accepted**. The price is that requests that arrive at the same instant at the edge can all be refused (each sees the others); the form uploads one photo at a time, so an honest client does not meet this. The photo use is taken in middleware before the body is read, so a refused upload costs no decoding and no R2 write, and it **stays taken when the upload then fails** (413, 415, 422): an undecodable image already cost CPU. `createRecipe` takes the Recipe use after the resend lookup and on `db` itself, not inside its transaction (inside it the row would stay invisible to others until commit), and gives it back when it publishes nothing (a rejected input, or the answer to a resend that raced it). Reserving takes no lock that is held while anything else is locked (the insert's `FOR KEY SHARE` on the Member is last in the Lock order anyway), so the Lock order is unchanged. `createRecipe` applies `DAILY_LIMITS.recipe` by default; only the demo seed passes `dailyLimit: null`. Rows older than 24 hours are deleted on the Member's next upload (best effort, a failure is only logged) and for every Member by `pnpm photos:sweep`.

Input bounds: `GET /api/recipes` takes at most 10 `keyword` terms and 20 `ingredientIds` / 20 `baseIds` (400 `invalid_query` beyond that); `GET /api/ingredients/suggest` takes a `name` of at most 100 characters (400); JSON bodies of `POST`/`PUT /api/recipes` and `POST /api/ingredients` (and the ABV `PATCH`) are limited to 64KB (413 `too_large`).

### Social UI

`/members/[username]` is the profile (tabs: Recipes, Following, Followers, and Saved for the owner only; others get 404). `/members/[username]/edit` changes Username, bio and icon; `/withdraw` is the withdrawal confirmation (no grace period, FR-058), which also deletes the stored photos. The Recipe detail page mounts `LikeButton` and `SaveButton` (`#lib/components`), with their initial state from `getReactions` in the page load (server-rendered, no flicker); Like shows a count only and is hidden on one's own Recipe, Save is for signed-in Members. The owner also gets an edit link and a confirmed delete (`?/delete`, which also removes the Likes, Saves and stored photos), and an Administrator gets the delete alone (no notice to the author, FR-074). The author's name on the detail page and the list cards links to `/members/[username]`.

## Auth

Better Auth runs inside the app (ADR 0005); its endpoints are under `/api/auth/*`. Google and LINE only, no email/password. Set the `BETTER_AUTH_*`, `GOOGLE_*` and `LINE_*` variables from `.env.example`.

**`member` is Better Auth's user table** (`user.modelName: 'member'`), so withdrawal and Suspension run in the app's own transactions. `account`, `session`, `verification` and `rate_limit` are Better Auth's tables in the same database; all ids are uuids.

| Better Auth user field           | `member` column                                                                 |
| -------------------------------- | ------------------------------------------------------------------------------- |
| `name`                           | `username`: stored as null at sign-up, set on `/welcome` (FR-052)               |
| `image`                          | `icon_key`: stored as null; the provider's photo URL is not kept                |
| `email`                          | `email`: always null (see below)                                                |
| `emailVerified`                  | `email_verified`: always false                                                  |
| `isAdministrator`, `suspendedAt` | `is_administrator`, `suspended_at` (additional fields, not writable by clients) |

- **No email is stored.** LINE may not return one (FR-050), and Better Auth matches a new login to an existing user by email, which would join a LINE login to a Google Member (FR-051). LINE logins without an email get a throwaway `<sub>@line.invalid` only to pass Better Auth's check; the create hook drops it.
- **One provider per Member** (FR-051) is enforced by `account`: unique `(provider_id, account_id)`, unique `user_id`, and `provider_id IN ('google', 'line')`. Account linking and `/link-social` are off; so are `/update-user`, `/update-session`, `/delete-user`, `/change-email` and `/unlink-account` (our services own those).
- **Suspension** (FR-075): a session is refused at creation if `suspended_at` is set, and every request re-reads the session from the database (no cookie cache); a suspended Member's sessions are deleted and `locals.member` is null.
- **Login start and rate limit** (#65): the OAuth state is kept in an encrypted, HttpOnly, `SameSite=Lax` cookie (`account.storeStateStrategy: 'cookie'`), so starting a login writes no `verification` row. The browser that starts must be the one the provider sends back (a return without the cookie, or with another login's, is refused as `state_mismatch`); Lax still sends the cookie on the provider's top-level GET redirect. There is one state cookie per browser: a second login started in another tab replaces it, and the first tab's return then fails with `state_mismatch`. `/login?/google` and `/login?/line` call Better Auth's HTTP handler (not `api.signInSocial`), so the sign-in rate limit applies: 10 starts per 60 s per client address (`LOGIN_RATE_LIMIT`), counted in the `rate_limit` table (`rateLimit.storage: 'database'`; the default in-memory counter is per serverless instance and limits nothing). The 11th gets 429 and a message on `/login`. The request to the handler is built by the action with the app's own origin, so Better Auth's origin check passes by construction; the rate limit is all this route buys. The client address is Vercel's `x-vercel-forwarded-for` (`CLIENT_IP_HEADER`), which Vercel sets itself even behind another proxy; `x-forwarded-for` is never used, because a client can send it. Where the header is absent (local, tests) all requests share one bucket; a value of several addresses does too. Better Auth rate-limits before it looks up a route, so any path under `/api/auth/*` would cost a database row: `isAuthEndpoint` (`#lib/server/auth/endpoints.js`, called from `hooks.server.ts`) lets only `GET /api/auth/callback/(google|line)` through and answers 404 to the rest (sessions are read in-process, not through `/api/auth/get-session`). Those two paths use Better Auth's default of 100 per 10 s per address. `rate_limit` rows hold client addresses: Better Auth prunes rows when a window rolls over, and the login action deletes rows idle for more than an hour (`pruneRateLimit`) on 1 in 20 requests; the table is left out of the backup (see Backup). After deploying this, apply the migration that creates `rate_limit` first: without it every `/api/auth/*` request and every login start fails.
- **Reserved Usernames** (#67): `admin`, `support`, `staff` and the like (`isReservedUsername` in `#lib/server/services/members`, compared in lower case) cannot be chosen on `/welcome` or `/members/[username]/edit`. A Member who already holds one keeps it and can still edit the rest of the profile; only switching to a reserved name is refused. Check before launch: `select username from member where lower(username) in ('admin','administrator','support','staff','moderator','mod','official','system','root','null','undefined','cocktail_party','cocktailparty','cocktail_party_official')`. The seeded demo Member (`demo_bartender`) is not affected.
- `src/hooks.server.ts` runs `authHandle` before `apiHandle`. `locals.member` (`{ id, username, isAdministrator }` or null) reaches Hono as `c.env.locals.member`. Guards: `requireMember`, `requireAdministrator` and `authorizePhotoUpload` in `#lib/server/auth/guards.js`. A Member without a Username is redirected to `/welcome` and gets 403 from guarded API routes.
- Withdrawal: `withdrawMember` in `#lib/server/services/members` deletes everything in one transaction and returns the storage keys to delete: Main and extra Photos, the icon, and both files of every `photo_upload` row of the Member, used or not (the rows go with the Member). It takes its locks in the Lock order described under Photo ownership (API section), so a withdrawal and a Recipe write by the same Member cannot deadlock. The `/withdraw` action runs it first; only once it has committed does it delete the objects with `deleteObjects` (best effort, each failed key logged) and sign out, so a failed withdrawal leaves the Member signed in to retry. Reachable without a Username, like `/welcome` and `/logout`.

The db tests drive Better Auth's real sign-in and callback for LINE with the token endpoint stubbed. A real Google login has been confirmed on a Preview; a real LINE login has not been tried.

## Age Gate (FR-060..062)

The root layout also renders the site header (sign-in-dependent links: own profile, saved Recipes, new Recipe, `/admin` for Administrators) and footer (`/terms`, `/privacy`); `/withdraw` is linked from the own profile page. It shows a modal asking the visitor to declare they are 20+ until the `age_gate_consent` cookie exists. `+layout.server.ts` reads the cookie; the "yes" button posts to `POST /age-gate` (`src/routes/age-gate/+server.ts`), which sets the cookie for 30 days (HttpOnly, SameSite=Lax) and redirects back to a same-origin path. "No" is a link to `?age-gate=declined`, which swaps the question for a "not available under 20" message and adds `<meta name="robots" content="noindex">` (the page behind it is a duplicate); no cookie is set. Cookie name, lifetime and the helpers are in `src/lib/age-gate.ts`; the gate itself is `AgeGate.svelte`.

`/terms` and `/privacy` are exempt from the gate (`isAgeGateExempt`).

The page is always server-rendered (FR-062): while the gate is open its container is only `inert` (which also keeps keyboard focus inside the dialog) and covered by the overlay, and `<html>` stops scrolling. The gate works without JavaScript. Playwright runs every spec with the consent cookie set (`playwright.config.ts`); `e2e/age-gate.e2e.ts` clears it.

## Browsing: top page and Recipe detail (FR-040..046, FR-062, FR-080)

Both pages are public, server-rendered and read through the services directly (no HTTP hop to `/api`): the load functions call `searchRecipes` / `getRecipeDetail`, so the body is always in the HTML, behind the Age Gate too.

- **`/`** is a plain GET form, so every search is a shareable URL and works without JavaScript. Query: `q` keyword, `ing` (repeated; all must be in the Recipe), `only=1` (only these Ingredients; needs at least one `ing`), `base` (repeated; any), `abvMin`, `abvMax`, `na=1` (Non-alcoholic), `sort=new|like`, `cursor`. The "次のページ" link carries the keyset `cursor` of the same search; there is no previous-page link (use the browser's back or "最初のページへ"). A malformed query (bad cursor, id or number) answers 400. Any page with a query string (a search, a sort, a cursor, or an untouched form's `?q=&sort=new`) carries `<meta name="robots" content="noindex">`; only the plain top page and Recipe detail are for search engines (NFR-007). A page costs three queries: the list, the Bases of the listed Recipes, and the Ingredient master for the form.
- **`/recipes/[id]`** shows the Recipe with its Ingredients (Mix Ratio as a bare number), steps, Alcohol Content ("目安"; an override is labelled "投稿者による修正値") and extra Photos. Unknown, malformed ids and Recipes of suspended Members are 404. OGP: `og:title`, `og:description`, `og:url`, and `og:image` = the Main Photo's `detail.webp` (`twitter:card` `summary_large_image`).
- **Report and `/admin`** (FR-070–076): a signed-in Member sees "このレシピを通報する" on the Recipe page (form action `?/report`). `/admin` (Administrator only: 401→login, 403 otherwise; `noindex`) lists Reports (`?status=open\|resolved\|dismissed\|all`, default `open`; 50 per page, newest first, with a plain "次へ" link carrying `?cursor=`; a malformed cursor shows the first page) and changes their status, deletes the reported Recipe (behind a `<details>` confirmation that says the author is not notified and the Report stays; works without JavaScript, like the delete on the Recipe page), suspends/unsuspends Members, registers alcoholic Ingredients / edits their ABV, and deletes 0% Ingredients that no Recipe uses (#64). Reports keep `target_state` (`recipe_deleted`, `member_withdrawn`) and no Recipe content once the Recipe is gone (FR-074/078); a deleted Recipe is not notified to its author. The first Administrator is made by hand: after they have logged in once, run `update member set is_administrator = true where username = '<username>';`. The page calls the services directly; the Hono routes above expose the same services.
- Image `alt` is generated from the Recipe title (`<title>の写真`, NFR-005).
- Photo URLs come from `photoUrl(key, 'list'|'detail')` (`services/images/url.ts`): `R2_PUBLIC_BASE_URL` plus the stored key, with the stored `list.webp`/`detail.webp` key swapped for the wanted size. Without `R2_PUBLIC_BASE_URL` no image is rendered (a "写真なし" box on the list, no `og:image`).
- The e2e job needs the app database (`DATABASE_URL`, migrated): `e2e/browse.e2e.ts` inserts its own rows with SQL and removes them afterwards. `e2e/recipe-form-signed-in.e2e.ts`, `e2e/recipe-detail-actions.e2e.ts`, `e2e/report.e2e.ts` and `e2e/admin.e2e.ts` sign a Member in by inserting a session row and signing the cookie with a fixed test secret (`e2e/signed-in.ts`, handed to the server by `playwright.config.ts`); photo uploads are answered by the spec, since R2 is not reachable. The Report and administrator specs publish their Recipes through `POST /api/recipes` with a seeded photo upload, and remove their Members, Reports, Recipes and Ingredients (own `e2e_rpt_` / `e2e_adm_` / `E2E通報` / `E2E管理` prefixes; the other signed-in specs use `e2e_form_` and `e2e_det_`). The specs share one `pool` (`e2e/signed-in.ts`) and none of them ends it afterwards. CI starts a Postgres service for it.

## Branches, CI and deploy

Work on a branch off `develop` and open a PR into `develop`; link the issue with `Closes #N`. Merging needs the CI workflow green (`check`, `lint`, `test`, `build`, `test:db`).

## Preview (Vercel + Neon + R2 + OAuth)

Steps and pitfalls for bringing up a Preview, the environment that "What is still unchecked" above is run on. No secrets here: values go only into the Vercel project's variables. Photos, Auth and Backup are described in their own sections.

**Neon**

1. Create a project (region near `sin1`, see below). Use one branch for `production` and one for `preview`, each with its own connection strings. Create `preview` before `production` holds real Members: a branch copies its parent's data.
2. Every branch has a **Direct** string (host without `-pooler`) and a **Pooled** one (`-pooler`, PgBouncer in transaction mode). **The current Preview's `DATABASE_URL` is the Direct string; whether to go back to Pooled is undecided.** Pooled is the usual choice for functions: every function instance opens its own connections, and the direct limit (`max_connections` minus 7 reserved; 97 on a 0.25 CU compute, the smallest, so check `SHOW max_connections`, unverified for this project) is easy to exhaust. The app's pool is small for that reason (see Notes). `pnpm db:migrate`, the seeds and `pg_dump` always use **Direct**; they need session behaviour, which a transaction pooler does not give. Before switching the app to Pooled, see "Before switching back to Pooled" below.
3. Neon's strings end in `sslmode=require`. For what **node-postgres** reads (the app's `DATABASE_URL`, `pnpm db:migrate`, the seed and sweep scripts), change it to `sslmode=verify-full`: pg treats `require` as `verify-full` today and warns that v9 changes it. The connection string is not rewritten in code. **Do not do this for `pg_dump`** (the Backup workflow's `DATABASE_URL` secret): that is libpq, where `verify-full` needs a root certificate file, so keep `sslmode=require` there. (`sslmode=verify-full&sslrootcert=system` might work with libpq; not tried, unverified. `backup.yml` has not run against Neon yet.)
4. Migrate the new branch from your shell, with the Direct string typed in so it stays out of the history and files:

   ```sh
   read -rs DATABASE_URL && export DATABASE_URL   # paste the Direct string, Enter; nothing is echoed
   pnpm db:migrate
   pnpm db:seed:ingredients                       # optional, see Run
   unset DATABASE_URL
   ```

   Skipping this makes the first sign-in fail with `relation "verification" does not exist` (Better Auth's table). Apply the migration that creates `rate_limit` before deploying code that uses it: without the table every `/api/auth/*` request and every login start fails. Run it again whenever `drizzle/` gains a migration; keep migrations backward compatible, because the running Preview keeps serving until the next deploy.

**Vercel**

1. Import the repository with the **SvelteKit** preset and Node.js **22** (Project Settings, Build and Deployment). The function region is fixed to `sin1` in `vite.config.ts`; nothing to set.
2. Add the variables of `.env.example` (`DATABASE_URL`, `BETTER_AUTH_*`, `GOOGLE_*`, `LINE_*`, `R2_*`) for the **Preview** environment only. `BETTER_AUTH_SECRET` is `openssl rand -base64 32`; use a different value from production. Neon's child branch probably keeps its parent's roles and passwords (unverified); reset the password if the `preview` branch should not share the production one.
3. **A deployment keeps the variables and code it was built with.** After changing a variable, **Redeploy**; the old deployments (and their URLs) do not change. Redeploy the **branch's latest** deployment: Redeploy on an old deployment rebuilds that deployment's old code.
4. A variable set for "Preview" applies to every preview, so a PR's preview also gets the `develop` branch URL as `BETTER_AUTH_URL`. Test sign-in on `develop` only: on a PR preview the callback goes to `develop`'s URL, not the PR's.
5. Whether Previews sit behind Vercel's Deployment Protection by default is unverified; check Project Settings, Deployment Protection. If it is on, be signed in to Vercel in the browser you test with, or relax it for the test.

**Which URL: the branch URL, not the deployment URL**

Each deployment has a unique URL (`cocktail-party-<random>-<team>.vercel.app`) that is frozen to the variables and code of that deployment. The branch has a stable URL (`cocktail-party-git-develop-<team>.vercel.app`) that always serves the branch's latest deployment. Use only the **branch URL** for `BETTER_AUTH_URL`, the OAuth callbacks and when testing. A unique URL as `BETTER_AUTH_URL` is wrong after the next deploy, and opening an old deployment shows what it was built with: `password authentication failed` after `DATABASE_URL` was fixed, or `redirect_uri_mismatch` after `BETTER_AUTH_URL` or an OAuth setting was fixed. If you see these, check you are on the branch URL and have redeployed.

**Google** (Cloud Console, OAuth client of type Web): Authorized JavaScript origins `<BETTER_AUTH_URL>`; Authorized redirect URIs `<BETTER_AUTH_URL>/api/auth/callback/google`. On the consent screen, a publishing status of Testing lets only the listed test users sign in; add yourself or publish it. Signing in with Google on the Preview has been confirmed.

**LINE** (LINE Developers, LINE Login channel): Callback URL `<BETTER_AUTH_URL>/api/auth/callback/line`. Unverified: while the channel is Developing, only its admins and testers can sign in (this is LINE's documented model as far as I know; check the channel page). A LINE login may return no email (FR-050); the app handles it (Auth section). LINE sign-in on the Preview has not been tried.

**R2** (Cloudflare): the Photo bucket is served publicly (custom domain, or `r2.dev` for a trial; `R2_PUBLIC_BASE_URL` is that base URL). The backup bucket is private: no public access, no custom domain (Backup section). An R2 API token is limited to chosen buckets: make one per bucket, Object Read & Write, and never let the Photo token reach the backup bucket or the reverse.

**Before switching back to Pooled**

The db tests and the Preview run on a direct or local connection, so nothing below has run through Neon's PgBouncer (transaction mode). On a Preview with the Pooled string, try each of these before relying on it:

- creating and editing a Recipe (interactive transaction with row locks, Lock order under API);
- registering a new Ingredient (`pg_advisory_xact_lock`, transaction-scoped, expected to work);
- searching (`pg_trgm`);
- `pnpm photos:sweep` (`FOR UPDATE SKIP LOCKED`).

When adding code later, remember Neon's PgBouncer does not support `SET`, session-level advisory locks, `LISTEN` / `NOTIFY` or SQL-level `PREPARE` (a drizzle `.prepare('name')` among them).

## Recipe form (FR-001..007, FR-020..023)

`/recipes/new` and `/recipes/<id>/edit` (`RecipeForm.svelte`) are for Members: signed out redirects to `/login`, and `/edit` answers 403 for someone else's Recipe and 404 for a missing one. The form posts through the typed client (`POST /api/recipes`, `PUT /api/recipes/:id`) and goes to `/recipes/<id>` afterwards.

- **Photos:** one required Main Photo and up to 3 more, each picked with `PhotoPicker` and uploaded at once to `POST /api/photos?kind=recipe`. The form keeps and sends the `.../list.webp` key of each stored pair (`mainPhotoKey`, `extraPhotoKeys`); the detail size is the same key with `detail.webp`. A photo that is replaced or removed before saving stays in storage unreferenced.
- **Ingredients:** `IngredientPicker.svelte` searches with `GET /api/ingredients/suggest` and shows similar names (FR-014). If no result matches the typed name exactly, "register as a 0% Ingredient" calls `POST /api/ingredients` with `abvPercent: 0` (FR-012). A Member over the registration limit gets a message instead (429, see "Ingredient limits and cleanup"). Alcoholic Ingredients can only come from an Administrator, so the form never offers to create one.
- **Alcohol Content:** the form computes the auto value live with the same rules as the server (`#lib/domain/alcohol`, via `src/lib/recipe-form.ts`). With alcohol, the Member may type an override in 0 < x ≤ the highest Ingredient ABV (shown as "投稿者による修正値", with the auto value beside it); editing Ingredients keeps it, "再計算する" clears it. An override that stops fitting after an Ingredient change blocks saving until it is fixed or cleared. Without alcohol the value is fixed at 0% and any typed override is dropped. Every save sends the override the form shows (`abvOverride` number or `null`), so the stored value always matches the screen.

## Photos (ADR 0003)

`PhotoPicker.svelte` shrinks a selected photo (JPEG/PNG/WebP, up to 10MB) below 4.5MB in the browser; `POST /api/photos?kind=recipe|member` takes the raw bytes as `application/octet-stream`, and `storePhoto` re-encodes them with `sharp` into two metadata-free WebP files (`<kind>/<id>/list.webp` 480px, `detail.webp` 1600px) in R2. The original is never stored. The route is behind `requireMember` (401 signed out, 403 without a Username) and records the upload against the Member (see API, "Photo ownership"). R2 is configured by the `R2_*` variables (declared in `src/env.ts`, examples in `.env.example`), read on the first upload. Derivatives are served with `Cache-Control: public, max-age=3600`, so a deleted Photo can still be fetched from an edge or browser cache for up to about an hour. `/dev/photo-picker` is the e2e harness page (uploads nothing); it returns 404 unless `E2E_HARNESS=1`, which only `playwright.config.ts` sets. Set `PW_REUSE_SERVER=1` to let `pnpm test:e2e` reuse an already running preview server on port 4173 (off by default, since another worktree may own that port).

Image processing load (#63): the server refuses anything over `MAX_PIXELS` = 30 million pixels (`too_many_pixels`, shown to the Member as "解像度が高すぎます"). The browser shrinks every photo of 4.5MB or more to at most 4096px on the long edge (16.8MP) before sending, so only a photo that already fits in 4.5MB at a higher resolution (a flat, highly compressible 30MP+ image) is refused. `processUpload` makes the two derivatives one after the other: each `clone()` decodes the input again, and decoding both at once doubled the peak memory.

### Known limits

- Browser downsizing is tested only on desktop Chromium (`e2e/photo.e2e.ts`). Untested: iOS Safari HEIC handling (expected to arrive as JPEG via `accept`, else rejected as an unsupported format), iOS canvas memory caps with 48MP/panorama photos, `imageOrientation: 'from-image'` on Safari ≤16.4 and old Android WebViews, Android Chrome's Google Photos picker (`file.type`, cloud-only photos), and downsizing speed on low-end phones.
- `sharp` loading in the Vercel function runtime is not verified. The local build bundles `@img/sharp-linux-x64`; deploy once to a Preview and hit `/api/photos` before relying on it.
- The R2 store is unit-tested for request construction only (no credentials in CI); it has not talked to a real bucket.
- The unused-upload sweep is not scheduled: `.github/workflows/sweep-photos.yml` is manual (`workflow_dispatch`, `main` only) until the `production` environment has `DATABASE_URL` and the `R2_*` secrets; then add the `schedule` it describes. The script has run only against a local database with dummy R2 credentials.
- A photo that fits in 4.5MB but has more than 30 million pixels (for example a very long stitched screenshot) is refused by the server with `too_many_pixels`: the browser only shrinks files of 4.5MB or more, and does not look at the pixel count.
- A storage deletion that fails after its commit is only logged: `deleteObjects` writes one `photo cleanup failed` line per failed key (one line listing every key when the store cannot be built), on every path (Recipe edit and delete, the `/admin` Recipe deletion, icon change, withdrawal, the sweep). The `photo_upload` row is already gone, so nothing retries it, and Vercel keeps runtime logs only briefly. Leftover objects can be found by listing R2 against the database; the sweep works from `photo_upload` rows, so it does not find them.
